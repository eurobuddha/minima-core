## What this file does

CommandRunner connects textual commands to command objects. It owns the registry of prototypes, parses parameter values, checks accepted parameter names and caller permissions, executes a sequence, and stops at the first failed result. [Command](Command.md) supplies the common parameter/reply API; each concrete command implements its own behavior. A parser can be correct while some registered operations are still missing from the port.

`getRunner` creates a new runner. `getCommandOnly` performs exact-name lookup and returns a fresh command from its prototype, or null if no prototype matches. `getCommand` first tokenizes a complete input, lowercases its command name, finds a fresh command, and fills its parameter object. It returns a `missingcmd` object for recognized parsing failures such as an unknown command, rather than returning a successful no-op.

## Two tokenizers, selected by the input

The fast path is attempted when the text has no opening brace, no opening square bracket and no Windows-style colon-backslash sequence. It trims the input, adds spaces around **every colon**, then uses a quoted-string-or-nonwhitespace regular expression. It retains the first token as the command and combines later tokens into name/value pairs. If a colon appears where a parameter name should begin, it returns null and the caller retries the normal path. A dangling name can be left out of the result. These rules are the pinned parser's behavior; they are not a general shell grammar.

The normal path scans the trimmed string, accumulating a token while tracking a quote flag and a combined brace/bracket depth. A literal space ends a token only outside quotes at depth zero. Quotes inside positive JSON depth are retained; quotes outside it toggle grouping and are removed. Braces and brackets change depth without a full JSON string/escape analysis. This stage groups text; the JSON parser checks an object or array later. Tabs and newlines are not identical to a literal space in this path.

## Interpreting parameter values

After lookup, the command stores the complete original command text. Every remaining token must contain a colon. The runner splits at its first colon and trims the resulting name and value. Duplicate parameter names overwrite earlier values in the command's JSON object.

A value beginning and ending with braces is parsed as a JSON object. A bracketed value is parsed as a JSON array **except for txnstate**, where it remains a string so bracketed state text can be supplied. A JSON ParseException becomes a missing-command error describing the bad parameter. Other strings have one leading and one trailing quote removed when present, then are stored as strings. Parsing a number-looking parameter does not make it a numeric JSON value unless it occurs within parsed JSON; the command's getter can convert that string later.

Unknown lookup and malformed parameters create missingcmd replies with status false. Empty input can fail earlier when the runner accesses the nonexistent first token; not every invalid input is converted into a missingcmd object.

## A command batch is an ordered sequence, not a transaction

`runMultiCommand` splits the input at semicolons with StringTokenizer. Empty delimiter runs produce no command token, but a whitespace-only token can survive until trimming/parsing. Semicolon splitting happens **before** quote/JSON tokenization, so a semicolon inside a quoted parameter still divides the batch.

For each token, the runner trims it, parses a command, and sets the caller ID. It then checks these stages in order:

1. Compare every supplied parameter name with the command's valid-name list. On the first invalid name, append a failure containing command text, parameters, status false, pending false and the invalid-name error, then stop the batch.
2. Ask `isCommandAllowed` about the parsed command name. The source has a fixed list of write-command names. Caller ID `0x00` is treated as admin; a different caller is rejected for a listed write command with an admin-privilege error and pending false. The older pending-approval/MDS logic visible in comments is inactive in this pinned file.
3. Call runCommand. A CommandException uses its message in the command's standard JSON reply. A different Exception is logged and contributes its toString form. Both replies receive status false.
4. Append the result and stop if its status is false. Otherwise continue with the next command.

Successful earlier commands are not rolled back after a later failure. Errors during parsing, validation, permission checks or result-status access lie outside the runCommand catch block. Logging itself can also throw from within a catch body.

`isCommandAllowed` trims its input and performs an exact, case-sensitive lookup in the write-name list. The normal parse path has already lowercased the name; calling this public helper directly with uppercase text is a different observation. `runSingleCommand` still executes the complete batch, then returns its first result or an empty object if there were no results. Its name does not limit execution to the first semicolon-delimited command.

## Native reuse and remaining differences

The native runner reuses Command, the native JSON parser, Java-style lowercasing and missingcmd. It uses shared command prototypes to construct fresh command receivers, retaining parameter ownership through shared JSON objects. The source's registry is larger than the currently implemented native registry; absent concrete commands have not been represented by fake successful implementations.

The native generic runCommand catch now calls the actual MinimaLogger through NativeThrowable, preserves I/O exception names, and rethrows native JavaError and std::bad_alloc representations before its generic Exception handler. Negative/empty indexes, null strings/prototypes, regex/Unicode corner cases and arbitrary registry mutation retain further parity gaps. The tests below intentionally do not claim to cover those complete boundaries.

## What the existing tests actually do

[CommandRunnerOracle.java](../../../../../../../support/CommandRunnerOracle.java) runs the pinned runner with three controlled fixture command names: fixture, send and txnstate. The [native harness](../../../../../../../support/command_runner.cpp) supplies corresponding fixture objects. Their bodies return normal reply/caller data or throw CommandException when a fail parameter is true. The mock send command allows the permission boundary to be tested without sending funds; it is not evidence that the real send implementation works. Concrete hash cases also run through the registry.

The [driver](../../../../../../../tools/command_runner_differential.py) combines 22 explicit inputs with 500 reproducibly generated strings. It tests fast splitting and full parsing for each, executes the explicit cases under admin and non-admin callers, checks the single-result wrapper, probes exact registry lookup, and varies case/spacing around write-command names. Inputs include JSON objects/arrays, duplicate parameters, missing colons, quotes, Windows paths, Unicode, malformed JSON and quoted semicolons.

The current normal and sanitizer reports each contain **1,265 comparisons, all passed**. The harness compares serialized observations exactly, but converts unexpected exceptions to the generic string ERROR and filters logger-prefix lines. This can hide differences in exception class, text and logging. Complete registry coverage and real wallet/network side effects are explicitly excluded. This suite was rerun successfully in both builds after the catch correction; no wallet command was executed.

## New error-path experiment

The [command failure lab](../../../../../../new-tests/command-runner-errors.md) compared 1,120 requests at its original checkpoint using the actual runner and logger with controlled command bodies. It checks returned JSON, escaped exception class/message, ordered log bodies, entry events, permission and invalid-parameter gates, and first/second logger failures. The original 896-request baseline had 450 mismatches; the corrected code has zero in normal and ASAN/UBSAN builds. Only timestamp/memory prefixes and generated frame lines are removed. All nine affected selected suites pass, including the real HTTP handler after its sandbox socket restriction was lifted. The fixture send command still performs no transfer.

## Check your understanding

1. A batch succeeds once, then supplies an invalid parameter to the next command. Does the first command's effect disappear? **Answer:** no; there is no rollback.
2. Does runSingleCommand guarantee that only the first command executes? **Answer:** no; it calls the batch runner and returns only the first result.
3. Why use a fixture named send in a permission test? **Answer:** to observe the runner's permission decision without making the test perform an actual transfer. It does not validate production send behavior.
4. Why retain the txnstate exception to JSON-array parsing? **Answer:** bracketed state text must remain a string on that source path.

The [wallet-wrapper comparison](../../../../../../../tools/wallet_wrappers_differential.py) also exercises a child rejection through the actual public runner. A missing child error becomes `error:null`; an embedded NUL inside an error string preserves all following characters. CommandException.getMessage supplies the complete nullable message, so these expected rejections do not enter generic exception logging.

## Child status after execution

The wallet-consolidation comparison exposed a missing-status mismatch: Java raised NullPointerException while native code reported bad_variant_access. The runner checks returned status after its command-execution catch block. That check now reuses CommandResult.status, preserving null unboxing and wrong-type cast categories. Four direct recorded-send probes and nested consolidation probes exercise this boundary; the final 247-program group passes in both builds. The [wallet-consolidation lab](../../../../../../new-tests/wallet-consolidation.md) records the full selected regressions. This does not broaden the exception catch region.

## Nullable replies and references

The runner now retains a nullable JSONValue returned by runCommand, appends it, and then reads status outside the catch block. Returning null therefore escapes as NullPointerException; returning an object with missing/null status also fails on that later access, and a non-Boolean status raises ClassCastException. No normal error reply is invented for these cases. The expanded error driver compares 1,680 requests with events and log order, including permission/parameter gates and logger failures. runSingleCommand retains an object return: a null batch result cannot reach its first-element return because the batch already failed at status access. See the [nullable-reply lab](../../../../../../new-tests/nullable-command-replies.md).
