## What this file does

Coordinates incoming proofs, full blocks and initial block download (IBD) on a message queue. It joins consensus validation to chain updates, database flags, archival storage and network notifications.

## Follow the logic

1. Posting a TxPoW first checks shutdown/restoration, stores it and emits NEWTXPOW when relevant or notification-all is enabled. Only then does the TxBlock-node flag suppress queuing. Posting a TxBlock requires that mode and stores both block and embedded TxPoW before queuing. Thus posting already changes state before processing begins.
2. Full proof processing uses a last-in-first-out stack. Ignore nonblocks, duplicates and blocks outside the permitted root/difficulty window. Find the parent in the tree; if absent, push a stored parent for another attempt. If present, require every referenced transaction and run the timed block checker.
3. After a valid full block, construct its TxBlock/MMR, store it, try broadcasting its ID, attach its tree node and push known children. Broadcast failure is caught and does not stop attachment. TxBlock-node processing follows the same traversal but uses checkTxBlockOnly on the supplied trusted block data.
4. Synchronization insertion has different checks: store block and proof first, then either create an empty tree root or attach to a known parent. For an empty tree with a cascade, check adjacent heights. A missing parent throws after the earlier database writes. Duplicate insertion returns false, although callers still increment their batch counter.
5. Tree recalculation acquires the database write lock and selects the heaviest branch. At the cascade depth-plus-frequency threshold, copy relevant ancestor coins to the new root, shorten the tree, mark removed proofs and transactions as cascaded, archive each block and append it to the cascade. Coin notifications and optional MegaMMR updates occur along the way; exceptions can leave earlier changes intact.
6. Prune MegaMMR, compact the cascade and clear sufficiently old cached TxBlocks. Then rebuild main-chain flags from the selected tip backward. Post MAIN_NEWBLOCK only when both old and new tips exist and their IDs differ. The Java finally block releases the write lock even when processing fails.
7. Main IBD validates its container, sets syncing true and may install a compatible cascade under a lock. After the first five minutes, a non-TxBlock node with a recent tip rejects nonempty compact-block input and requests further synchronization. Recent means strictly within three hours, or five minutes under test parameters, using absolute timestamp difference.
8. Process main IBD blocks in order, requesting missing transactions only for sufficiently recent blocks. Recalculate after 257 processed entries, including duplicates. A block exception disconnects and removes the peer, breaks the loop, then continues final recalculation and cleanup. The restoration-finished flag can therefore become true after this break; it is not a claim every received block succeeded. A finally block clears syncing.
9. Historical sync walks backward from the oldest archived block or tree root. Save a candidate only if its height is exactly one less and its hash matches the previous parent. Regardless of a height mismatch, advance lastpow to that candidate before the next iteration. Archive IBD uses forward insertion, recalculates after 1,001 entries and disconnects without peer removal on failure.
10. Synchronization requests skip internal UID 0x00 and honor NO_SYNC_IBD. Missing-transaction requests skip TxBlock mode and blocks strictly older than three hours; an IOException stops the remaining request loop and is logged. Other exception categories are outside that narrow catch.

## How the translation is approached

C++ retains shared message payloads and reuses MessageProcessor, tree/MMR/checker and database components. Explicit Main/network/clock callbacks make runtime dependencies observable without constructing the absent native Main. Factory creation starts the worker after ownership exists. withFinally models cleanup even during exceptions, including a cleanup exception replacing the original; atomic timer/finish fields support native access.

## What the tests tell us

The [Java oracle](../../../../../../../support/TxPoWProcessorOracle.java), [native service fixture](../../../../../../../support/TxPoWProcessorFixture.hpp), [native harness](../../../../../../../support/txpow_processor.cpp) and [driver](../../../../../../../tools/txpow_processor_differential.py) use Java-mined block bytes and actual processor/checker/tree/MMR code. The inspected report passes 384 programs and 1,434 operations. It compares queue contents, node/proof identity, nonces, MMR/cascade bytes, RAM flags, notifications, lock/sync state and receiver-call order. Cases include child-before-parent arrival, forks, mode/shutdown/restoration combinations, malformed IBD, batch boundaries and injected failures at successive receiver calls. An explicit guard requires the first case to attach a real six-block chain, preventing a matching but inert fixture from passing. The separate [native worker test](../../../../../../../support/txpow_processor_worker.cpp) asserts recovery after a null IBD, cleanup after 18 messages, retained ownership while a callback blocks, eventual release after stop, and 24 strict clock-boundary cases. These worker assertions are source-reviewed here; this documentation task did not run them. Recording archive/network receivers do not validate actual H2 or socket operation.
